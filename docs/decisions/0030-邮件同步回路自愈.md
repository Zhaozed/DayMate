# 0030 — 邮件同步回路自愈（per-tick 超时 + 看门狗 + 唤醒）

- **Date:** 2026-08-24
- **Status:** ✅ Accepted & implemented
- **Touches:** `src/main/app/container.ts` (`startEmailSyncLoop`)

## Context

ADR 0024 让同步回路（container-resident `setInterval`，每 `intervalSec` 跑一次
`syncFromEmails` → 漏斗 + 必读）成为邮件→必读/投递的唯一路径，并约定**空 delta
不烧 LLM**（成功 + 无新邮件 → 静默，不打 Activity）。ADR 0025 修了 mock/真实
provider 共存。

实际自用时发现一个静默停滞 bug：用户当天收到多封邮件，却一个新必读/投递都没
产出。排查 `activity_events`：最后一次 `provider_unavailable` 停在凌晨某点，
之后一片静默——既没有失败日志，也没有成功 surface。

根因：**provider 调用挂起（hang），而非 reject。** 半开 TCP / TLS 握手在网络
抖动中卡死 / 睡眠唤醒后连接失效——`net.fetch`（Gmail）或 `imap.connect()`
（163）的 promise 永不 settle。现有防线对此无效：

- `syncFromEmails` 内每个 provider 的 `try/catch` 只抓 **rejection**（网络断
  开时 `ERR_INTERNET_DISCONNECTED` / `ENOTFOUND` 会 reject → 打
  `provider_unavail`，这是之前能看到日志的原因）；挂起的 promise 不进 catch。
- 回路外层 `void tick().catch(() => {})` 同样只在 reject 时触发。
- `setInterval` 不等上一轮：tick N 挂起后，tick N+1、N+2… 照常派发，但每个都
  挂在同一个（或新一轮同样挂起的）provider 调用上 → 全部 pending、永不 reject
  → **永不打日志、永不恢复**。这正好解释了 01:53 后的静默。

163 `openImap` 每次 `new ImapFlow + connect`（非共享客户端），所以不是锁毒化；
纯粹是单次调用挂起 + setInterval 堆叠。

## Decision

在 `startEmailSyncLoop` 加三层自愈，provider 无关（同时覆盖 Gmail `net.fetch`
和 163 IMAP，不动每个 provider 的实现）：

1. **per-tick 硬超时**：`tick` 主体包进 `Promise.race([runTickBody(), timeout])`，
   `tickTimeoutMs = clamp(intervalMs - 10s, 60s, 120s)`。到点 reject → catch 打
   `provider_unavailable`（"邮件同步超时（疑似网络挂起，已自动跳过，等待下一轮
   重试）"）→ finally 释放 `inFlight`。挂起的调用被遗弃（泄漏一个 socket，
   下一轮开新连接，不毒化）。
2. **inFlight 重叠跳过**：tick 入口 `if (inFlight) return`——上一轮没结束就不派
   新 tick，避免堆 pending promise + 并发连 IMAP。
3. **看门狗 + 断路器**：记录 `lastSettledAt`。`3×interval` 无 settle 且
   `!inFlight` → 强制 tick（interval 自身停了 / 挂起漏过超时）。`5×interval` 仍
   `inFlight` → 超时机器本身挂了 → 断路器强重置 `inFlight=false` 再 tick。每
   `intervalMs` 巡一次。
4. **唤醒即时同步**：`powerMonitor.on('resume', tick)`——系统唤醒立即跑一轮。
   `setInterval` 睡眠期间被 OS 暂停、醒来不补跑漏掉的 slot；这是
   `morning_brief` cron 也有的已知局限（ADR 0016），同步回路自己兜住唤醒场景。

`lastSettledAt` 用 `Date.now()`（app 代码，非 workflow 脚本，可用）。看门狗
`setInterval` 不 `unref()`——这是 app 主回路，要保持存活。

## Key decisions / tradeoffs

- **provider 无关，不改 provider 实现**：per-tick 超时统一覆盖 Gmail/163，比给
  每个 provider 加 connect timeout / AbortController 简单且不漏。代价：挂起
  调用的 socket 泄漏一个（被 GC / 服务端踢掉），不毒化下一轮（163 每次新连接）。
- **不改"空 delta 静默"语义**（ADR 0024）：成功 + 无新邮件仍不打 Activity，
  避免每 180s 刷屏。看门狗只看 `lastSettledAt`，不看是否产 NTK——只有真停滞
  才打 `provider_unavailable`，成功轮次静默。
- **不动 node-cron**：morning_brief 的 cron 仍是 `0 9 * * 1-5`，睡过去仍漏
  触发（ADR 0016 已知）——本次只给同步回路加自愈，没碰 routine scheduler；
  routine 的唤醒补跑是后续可选项。
- **看门狗双阈值**：3× 强制 tick（停滞兜底）、5× 断路器（超时机器失效兜底）。
  两层冗余，避免单点。

## Limitations / next

- 没给 Gmail `net.fetch` / 163 `imap.connect()` 加各自的 connect timeout
  （per-tick 超时已覆盖；如要更细可在 provider 层加 AbortController /
  ImapFlow socketTimeout）。
- routine scheduler（morning_brief 等）的睡眠漏触发仍未补跑——同步回路自愈
  不覆盖 routine cron。
