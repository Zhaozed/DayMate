# 0031 — 邮件同步游标自纠正（cursor rewind）

- **Date:** 2026-08-24
- **Status:** ✅ Accepted & implemented
- **Touches:** `src/main/app/container.ts` (`startEmailSyncLoop`)

## Context

ADR 0030 给同步回路加了挂起自愈（per-tick 超时 + 看门狗 + 唤醒）。自用时发现
回路**没挂**、provider 也连上了（`providers=2 real=2`），却仍然一个新必读/投递
都不产出 —— ADR 0030 的 hang 自愈治不了这一类。

排查：在 `runTickBody` 加诊断 `console.log`（回路按 ADR 0024 空 delta 静默，一个
停滞和"没新邮件"长得一模一样，必须先打日志区分）。第一轮日志：

```
[email-sync] tick: providers=2 real=2 newEmails=0 cursor={mail163LastUid:1677387268, gmailLastInternalDate:1787414406000}
```

`real=2` → Gmail + 163 真实 provider 都正确换入（`refreshEmailProviders` 没问题），
凭证、`getStatus`、连接都没问题，也没 `provider_unavailable` —— 调用没挂、没
reject。但 `newEmails=0`。

再加一个**无游标探针**：空 delta 时对每个真实 provider 裸查最新 3 封 + 时间戳，
直接看"provider 眼里的最新邮件" vs 游标。探针结果暴露了矛盾：

```
probe gmail newest=3:
    gmail recv=2026-08-21T14:11:38Z subj=[student_ips] …   ← 最新 Gmail 邮件
probe mail163 newest=3:
    mail163 uid=1677387268 recv=2026-08-23T17:48:50Z       ← 最新 163 邮件
```

精确换算游标（之前少算一位）：`gmailLastInternalDate=1787414406000` ms =
**2026-08-22 16:00:06 UTC = 8月23日 00:00 CST**。而 Gmail 真实最新邮件是 Aug 21
14:11 UTC。**游标比真实最新邮件还靠前 ~26 小时**。

根因：**ADR 0025 未修的 follow-up —— "Gmail 游标被 mock 推进过头"。** mock
provider 当初把 `gmailLastInternalDate` 推到一个未来值，mock 移除后游标值留了下
来。后果：每轮 `listMessages`（newest-first）带这个靠前游标 → 真实邮件全部
`receivedAt <= sinceInternalDate` → 第一封就 break → 返回 `[]` → `newEmails=0`，
且因 ADR 0024 空 delta 静默，和"没新邮件"不可区分 —— 一个**幽灵停滞**：没报错、
没超时、没 Activity、provider 连着、却永远不产出。（163 游标 `1677387268` =
真实最新 uid，没污染，返回 0 是正确的。）

## Decision

在 `startEmailSyncLoop` 加**游标自纠正**一层（ADR 0030 hang 自愈之上的第二类自
愈），provider 无关（Gmail `internalDate` / 163 `uid` 各一条分支）：

1. **空 delta 时无游标探针**：`result.newEmails.length === 0` 时，对每个真实
   provider `listMessages({ limit: 1 })`（R0 只读，不持久化）取真实最新邮件。
2. **靠前即回退**：若游标 > 真实最新邮件的时间戳/uid（Gmail `cur > ts`；163
   `cur > uid`，uid 单调，只在 mock 污染下发生）→ 回退游标到 `最新值 - 1`（Gmail
   `ts - 1ms`；163 `uid - 1`），使下一轮该邮件 `> 新游标` → 被重新拉取处理。
3. **立即重跑**：回退后 `setTimeout(() => void tick(), 3_000)` —— 不等 180s，让
   纠正当轮生效。3s 延迟让当前 tick 的 `finally` 先释放 `inFlight`，re-tick 的
   `if (inFlight) return` 兜底。
4. **每会话每 provider 至多回退一次**：`rewoundProviders: Set<string>`。污染是
   一次性历史遗留，一次回退即修复。若后续某轮探针因竞态（邮件恰在探针后到达）
   返回"非真实最新"，`游标 == 真实最新` 但探针略旧 → 会误判为"靠前"。Set 闸把这
   种误判的后继回退全挡掉，**绝不出现每 180s 重复回退 → 重复分类同一批邮件 → 烧
   LLM 的循环**。后续真正的新邮件（`> 游标`）照常 surface，不受影响。

`newest - 1` 而非 `newest`：回退到 `newest` 会令 `newest <= newest` 立即 break →
被挡邮件仍不 surface；`newest - 1` 让该邮件 `> 新游标` → 被拉取 → 游标正常推进
到 `newest`，下一轮稳定（`newest <= newest` → 0，探针在 Set 内跳过 → 不再回退）。

## Key decisions / tradeoffs

- **provider 无关**：Gmail `internalDate`、163 `uid` 各一条分支，统一在回路层纠正，
  不改每个 provider 的 `listMessages`。
- **不改"空 delta 静默"语义**（ADR 0024）：成功 + 无新邮件仍不打 Activity。纠正
  探针只在 `newEmails===0` 时跑，且只 `console.log`（dev 控制台，非 Activity 刷屏）。
- **每会话一次回退**：污染是一次性历史遗留；Set 闸是循环兜底。代价：若同一次运
  行中污染复发（mock 再接入等），要到重启才再触发 —— 极罕见，可接受。
- **`newest - 1` 重处理代价**：回退后重跑会把"最新那一封"重新喂进漏斗/必读。幂
  等：漏斗按 messageId 去重 + normalized 投递去重；若最新邮件是学校群发/广告，pre-
  LLM 闸（`isSchoolSpam` / `ADS_KEYWORD_RE`）直接 drop，零 LLM。实测解封的 3 封里
  若含 `[student_ips]` 群发，即走此路径，不烧 LLM。
- **ADR 0030 的 hang 自愈仍保留**：本 ADR 治"游标污染"（幽灵停滞），ADR 0030 治
  "provider 调用挂起"（无 settle 停滞）。两类根因，两层自愈，互不替代。

## Limitations / next

- 探针 `listMessages({ limit: 1 })` 多一次 Gmail API / IMAP 调用，但只在空 delta
  时、每 provider 至多一次/会话 → 成本可忽略。
- 若污染复发于同一次运行（mock 再接入），需重启才再纠正（见上 tradeoff）。
- routine scheduler（morning_brief）的睡眠漏触发仍未补跑（ADR 0016/0030 已知）。
