# 群发邮件确定性预过滤（LLM 调用前过滤）

## Context

ADR 0022 把必读改成「邮件驱动实时」后，容器的 ~3 分钟邮件同步回路对**每封新邮件**
最多跑 3 次 LLM：`classify_application_email`（投递漏斗）+ `classify_inbox`（必读）+
`generate_draft_reply`（草稿）。用户 dev 启动后短时间内被烧了约 ¥2 LLM token
（deepseek-v4-flash）——根因是游标停在 ~3 天前，首启一次性补抓 3 天 delta 批量喂 LLM，
而 Gmail 收件箱大头是学校群发通知（讲座/食堂/教务/选课），对用户意义不大却照样烧 token
+ 发必读噪音。

用户的明确要求：

- **能判断群发 vs 真人**：学校群发通知意义不大，真正要进必读的是真人发的（导师/同学/HR 单发）。
- **Gmail = 学校事务，163 = 国内含求职**；广告/群发可忽略，但**不能误杀真正有用的邮件**。
- **关键**：「在给 LLM 处理之前，你最好是先过滤一遍，尽可能的稳定。」——群发判定走
  **确定性规则、不烧 LLM**，行为可预测、可单测。

核心矛盾：**投递确认信本身也是群发**（`noreply@…`、平台模板），却是投递漏斗的粮食
（ADR 0019 邮件驱动投递）。一条规则不能同时满足「必读跳群发」和「漏斗留投递确认」。
**解法是分路径过滤**——同一封 bulk 邮件在两条路径上走不同规则。

Verified: typecheck + lint + 397 tests（1 skipped）+ build 全绿。新增
`tests/unit/bulk-mail.test.ts`（9 测试）+ 扩展
`tests/integration/email-briefing-service.test.ts`（4 群发预过滤测试，含 spy runtime
断言 classify_inbox 不被调用）+ `tests/integration/email-sync.test.ts`（3 漏斗预过滤测试，
含 countingRuntime 断言 classify_application_email 不被调用）全绿。

## 决策

### 1. 纯函数层 — 新文件 `src/main/util/bulk-mail.ts`

所有判定集中成**纯函数 + 正则**，零 LLM、零副作用、完全可单测。放 `main/util`
（renderer 不可达，renderer 不需要）。

- `detectBulkFromHeaders(get)`：任一标准 RFC822 路由头命中即 true ——
  `Precedence` ∈ {bulk,list,junk}；`List-Id` 非空；`Auto-Submitted` ∈
  {auto-generated,auto-replied}；`List-Unsubscribe` 非空；`X-Mailing-List` 非空。
- `BULK_SENDER_RE`：`noreply/no-reply/notice/admin/mailer-daemon/postmaster/
  donotreply/notification/system/do-not-reply` 发件人。
- `SCHOOL_LIST_ALIAS_RE`：`all-students/undergraduate/graduates/all/students-all` 收件人别名
  （学校群发名单）。
- `isBulkMail(email)` = `email.bulk===true || BULK_SENDER_RE.test(from.address) ||
  收件人含 SCHOOL_LIST_ALIAS_RE`。
- `ADS_KEYWORD_RE`：从 `detectTopic`（`agent-runtime.ts`）抽出的营销/退订词
  （退订/unsubscribe/广告/优惠/促销/限时/折扣/coupon/营销/推广…）。`detectTopic` 改引用
  此常量，DRY。
- `IMPORTANT_BULK_KEYWORD_RE`：`毕业/学位/答辩/选课/缴费/签证/紧急/截止/offer/面试/录取/
  报到/注册/学费` —— 群发也救回必读的安全网。
- `shouldSkipBriefing(email)` = `isBulkMail(email) && !IMPORTANT_BULK_KEYWORD_RE.test(text)`
  —— 群发但无重要关键词 → 跳必读 LLM；群发但带毕业/缴费等 → 不跳（仍要 surface）。
- `shouldSkipFunnel(email)` = `isBulkMail(email) && ADS_KEYWORD_RE.test(text)`
  —— **仅纯营销 edm 跳漏斗**；投递确认信（bulk 但非 ads）保留。

### 2. `NormalizedEmail.bulk?: boolean`（`src/shared/types.ts`）

§17-safe 设计：**只持久化布尔，原始头不进 `NormalizedEmail`**。原始 RFC822 头值若随邮件
进 LLM prompt 会形成注入面；一个布尔没有注入面。`bulk?` 可选，既有夹具/测试不改即编译。

### 3. Provider 在 normalize 时算 `bulk`（头 provider 局部，不外泄）

- **Gmail**（`gmail-provider.ts` `normalizeGmailMessage`）：用既有 `header()` helper
  读 5 个 bulk 头 → `detectBulkFromHeaders` → 塞 `bulk` 进返回字面量。头只在 provider 局部。
- **163**（`mail-mime.ts` `ParsedMailLike` 加 `headers?` 透传 mailparser 的
  case-insensitive Map；`mail163-provider.ts` `toNormalized` 读 `parsed.headers?.get('list-id')`
  等 → `detectBulkFromHeaders` → 塞 `bulk`）。
- **Mock 夹具**：`mock-email-provider.ts` 加学校群发通知（`notice@school.edu.cn`，
  `to: all-students@`，纯通知无重要词，`bulk:true`）+ 招聘平台 edm（含退订/限时优惠）；
  `mock-mail163-provider.ts` 加投递确认 bulk（`noreply@zhipuai.com`，subject 含「投递成功」，
  `bulk:true` —— bulk 但非 ads，漏斗必须留）。

### 4. 必读路径过滤（`EmailBriefingService.briefNewEmails`）

在 `runAgentStep('classify_inbox')` **之前**两段分流：

1. **Bulk 段（零 LLM）**：对 `newEmails.filter(isBulkMail)` 逐封——若
   `IMPORTANT_BULK_KEYWORD_RE` 命中（毕业/缴费/答辩…）→ **确定性** surface 一个 high
   `【通知】${subject}` NTK（reason 标注「已确定性提取（未调 LM）」），不调 LLM；否则跳过。
2. **真人段（LLM）**：`humanEmails = newEmails.filter(e => !isBulkMail(e))`；若非空才跑
   `classify_inbox`，现有 urgent/high 分派 + auto-draft 逻辑不变，只是输入集收窄到真人邮件。
   `humanEmails.length===0` 时不发空 LLM 调用。

**关键设计取舍**（vs 初版计划）：初版打算 `shouldSkipBriefing` 字面保留（important-bulk 进 LLM 段
让 classify 处理）。但 `classify_inbox` 对 `!important && !actionable` 的邮件会 drop ——
群发毕业通知落到 general topic、无 reply cue → 被 classify 丢弃，既浪费 LLM 又不 surface。
**改为重要关键词群发确定性 surface、不走 LLM** —— 更省、更稳、更可预测（符合用户「稳定」要求）。

### 5. 投递漏斗路径过滤（`ApplicationService.syncFromEmails`）

在 `runAgentStep('classify_application_email')` **之前**：

- `funnelEmails = [...byMessageId.values()].filter(e => !shouldSkipFunnel(e))`。
- `funnelEmails.length===0` → 走现有「无邮件」早返回（**游标仍推进**，`newEmails` 返回全量
  供 briefing 路径自己分流）。
- 否则对 `funnelEmails` 跑 classify。结果按 messageId 回查 `byMessageId`（未变）。
- 保守：**只跳纯营销 edm**；投递确认/面试通知（bulk 非 ads）保留 → 漏斗照常建投递，不误杀。
  这正是用户担心的「别过滤掉真正有用的邮件」——投递确认信是 bulk 但是漏斗粮食，分路径规则保住了它。

## 降本效果

- Gmail 学校群发通知（讲座/食堂/教务/选课）→ 不再烧 `classify_inbox`、不发必读噪音。
- 招聘平台 edm（退订/限时优惠）→ 不再烧 `classify_application_email`（漏斗）也不进必读。
- `classify_inbox` 只对**真人邮件**跑；`classify_application_email` 只对**非纯 ads** 跑。
- 首启 3 天 delta 批量补抓时，群发邮件被确定性规则秒级过滤，不再批量喂 LLM。

## 设计取舍（稳定性）

- **纯确定性、零 LLM**：所有判定纯函数 + 正则，完全可单测、行为可预测 —— 用户要的「稳定」。
- **保守、不误杀**：必读带 `IMPORTANT_BULK_KEYWORD_RE` 安全网（毕业/缴费/答辩群发不漏）；
  漏斗只跳纯 ads（投递确认信非 ads → 保留建投递）。
- **§17-safe**：只 `bulk?: boolean` 持久化，原始头 provider 局部不外泄，过滤在 LLM 前
  不开新注入面。untrusted 检测（§17，在 classify 内部）与 bulk 正交、不冲突——两者都跳必读，
  各自独立。
- **向后兼容**：`bulk?` 可选，既有夹具/测试不改即编译。
- **DRY**：ads 正则抽共享，`detectTopic` 与漏斗过滤共用。
