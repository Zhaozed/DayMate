# ADR 0026 — 首页重构：今日天气 + 晨报轮播 + 可管理 ToDo（邮件自动抽取）

## 状态

Accepted — 2026-08-22

## 背景

首页（`Home.tsx`）自 M0 起一直是占位骨架：右上角「运行晨报」按钮 + 标语「用一份晨报开启新的一天」，下面两张低信息密度卡（近期动态 activity 流 + IPC 健康检查）。这些对用户没有实际用处——首页没有回答「今天长什么样」。

与此同时，ADR 0022–0025 已把邮件驱动做成主线：同步回路每轮对增量邮件跑 `classify_inbox`（必读路径，对 humanEmails）与 `classify_application_email`（漏斗路径，对 funnelEmails）两次 LLM，产出的结构化分类（reply / follow_up / 面试通知）**却没沉淀成 ToDo**。用户明确要求「从增量邮件里抽出有用的 ToDo」（只生成有用的、写清 163/gmail 来源、规划紧急程度、提到日期就带 dueAt），且**不新增 LLM 调用**。

## 决策

### A. 今日天气卡（真实天气 + LLM 润色，1 次/天）

- 新 `WeatherService`（`src/main/services/weather-service.ts`）：
  - `fetchWeather(city)`：用 Electron `net.fetch`（proxy-aware，复用 Gmail 同款）调 `https://wttr.in/{city}?format=j1`（免 key），取 current_condition（temp_C / FeelsLikeC / desc / humidity / windspeedKmph / weatherCode）+ 今天最高/最低温。
  - `refresh()`：取真实天气 → 跑 `generate_daily_weather` agent step（LLM 润色穿衣 + 宜忌文案）→ 缓存 → 返回 briefing。失败记录 Activity 并返回 undefined（Home 显空态 + 「生成」按钮）。
  - `getCached()`：读非密 `settings.json` 的 `weather` 块，日期 != 今天则视为过期。
- 新 agent step `generate_daily_weather`（`agent-runtime.ts`）：
  - 无 key 时确定性 stub（`weatherDescZh` 按 weatherCode 映射天气现象；`generateDailyWeather` 按体感温度区间映射穿衣、按降雨/暴晒/寒冷/大风映射实用宜忌，零 LLM）。
  - 有 key 时走真实 LLM：`buildUserMessage` 把 wttr.in 输出框成 `<weather_data>` DATA 块（§17 inert），要求中文化 summary + 穿衣 + 3 条宜 + 3 条忌（**实用向，非玄学**——玄学宜忌仍在运势 bubble）；输出走 `submit_daily_weather` TypeBox 工具（`structured-output.ts`）+ `weatherBriefingSchema` Zod 二次校验 + `enforceTrust` 截断兜底。
  - `prompt-injection.ts` 的 `buildSystemPrompt` 加 `generate_daily_weather` 任务分支。
- 缓存：`Settings` 加 `weather` / `weatherCity` 字段 + `readWeatherCache` / `writeWeatherCache` / `readWeatherCity`（默认北京）/ `writeWeatherCity` + `normalizeWeather` 校验。
- 每日 cron `27 8 * * *`（避开 :00 + 与 08:17 运势错峰），生成 + 缓存 + 推一个 robot 气泡（category 'fortune'）。

### B. 今日晨报轮播卡（kind 标记 + 历史 IPC + 左右翻看）

- `need_to_know` 表加 `kind TEXT`（nullable，幂等 ALTER）。`NeedToKnow` / `CreateNeedToKnowInput` / `NeedToKnowStep` 加 `kind?: 'morning_brief' | 'email'`。
- `listNeedToKnow()`（必读）filter `kind IS NULL OR kind != 'morning_brief'` → 晨报离开必读、进首页晨报卡。
- 新 `listMorningBriefs(days=7)`：`WHERE kind='morning_brief' AND createdAt > now-7d ORDER BY createdAt DESC`。
- `engine.ts` 的 `execNeedToKnowStep` 把 `step.kind` 透传给 `create`；`morning_brief` 模板的 publish step 设 `kind: 'morning_brief'`。
- IPC `MORNING_BRIEF_LIST` → `listMorningBriefs(7)`。Home 卡片左右箭头翻看近 7 天；今日无晨报则「生成今日晨报」按钮（调 `runRoutine('morning_brief'`)，替代被删的右上角手动按钮）。

### C. ToDo 管理 IPC + TaskService

- `TaskService` 加 `delete(id)`（硬删）。`Task` + `TaskCreateInput` 加 `sourceProvider?: 'gmail' | 'mail163'`（迁移 `tasks` 表加 `source_provider TEXT`）。
- IPC 新增 `TASK_CREATE`（input: TaskCreateInput）、`TASK_DELETE`；`TASK_UPDATE` / `TASK_LIST` 已有。
- 新增 `TASKS_CHANGED` 事件 + `onTasksChanged`（preload）。任务增/删/改/自动生成时 broadcast，Home 订阅实时刷新。

### D. 邮件自动抽 ToDo（折进已有 classify，零新增 LLM 调用）

- 扩展两个 LLM 输出 schema（`structured-output.ts` + Zod）：`submit_classifications` 与 `submit_application_email_classifications` 每条结果加 `todoTitle?: string` + `dueDate?: string`。
- prompt 指示：**仅当存在具体、可执行的下一步动作**才填 `todoTitle`（模型自判「有用的」过滤——没用的不填即不生成）；邮件提到日期/截止/面试时间则填 `dueDate`（相对词如「下周五」→ 模型算成具体 ISO 日期）。
- 确定性 stub（`agent-runtime.ts`）：
  - 必读 `classifyInbox`：reply/follow_up 才给 `todoTitle`（「跟进：{subject}」/「回复：{sender}」）；FYI/information 不给。`parseDueDate` 从 body 正则尽力解析成 ISO（today/tomorrow/下周五/8月25日/2026-08-25/8/25），解析不出则不填。
  - 漏斗 `classifyApplicationEmail`：interview/written_test 才给 `todoTitle`（「{company} 面试 · {position}」）+ dueDate；offer/applied/communicated 不给。
- 生成 ToDo 的落点（复用 classify 结果，不新增调用）：
  - `EmailBriefingService.briefNewEmails`（必读路径）：classify_inbox 跑完后，对有 `todoTitle` 的结果 → `taskService.create({...sourceProvider: email.provider, priority: <topic 映射：recruiting/fees_billing→urgent, meeting/follow_up→high, reply→medium>, dueAt: dueDate, description: reason})`。幂等 by sourceId（`email:{messageId}`）。注入 `taskService` + `onTasksChanged`。
  - `syncFromEmails`（漏斗路径，`application-service.ts`）：classify_application_email 跑完后，对有 `todoTitle` 的结果 → 同样 create Task（面试/笔试 urgent，其余 high）。`setTaskExtraction(taskService, onTasksChanged)` setter 注入。

### E. Home 页面重写（`Home.tsx`）

布局（去掉标语 + 运行晨报按钮）：grid-cols-2（今日天气 / 今日晨报轮播）+ 全宽 我的 ToDo。

## §17 安全

- **untrusted 邮件永远不产 ToDo**：`enforceTrust` 的 `classify_inbox` 与 `classify_application_email` 分支对 untrusted 结果强制 `todoTitle: undefined` + `dueDate: undefined`（确定性兜底，无论模型说什么）。stubs 也对 untrusted 分支不填。
- 天气输入是 wttr.in 的 inert DATA（非用户/外部 prose），框成 `<weather_data>` 块；`generate_daily_weather` 的 `enforceTrust` 截断 + 兜底非空 yi/ji。
- §15 不受影响（无新外部写入；ToDo 是本地 Task 表写入，R1）。

## 设计取舍

- **零新增 LLM 调用**：ToDo 抽取折进已有 classify（必读 humanEmails + 漏斗 funnelEmails），只加输出字段。天气 1 次/天（用户选的润色方案）。
- **「有用的」过滤 = 模型自判**：只有模型填了 todoTitle 才建 Task——直接对应用户「没用的别给我生产」。stub 也遵守（reply/follow_up + 面试/笔试才有）。
- **确定性优先级**：topic/eventType 映射 priority（稳定可测）；dueDate 由 LLM/stub 从邮件抽。
- **晨报/必读分离**：kind 列让晨报进首页轮播、离开必读，必读回归「邮件驱动 urgent/high」纯定位。
- **迁移幂等**：kind / source_provider 列 ALTER IF NOT EXISTS（M1 pattern）。
