# 瘦身：侧栏精简 + 例程裁剪 + 必读=邮件驱动实时 urgent/high + 草稿免审批

## Context

用户的实际用途收窄为两件事：**跟进攻秋招投递**、**跟进学校邮箱毕业相关事件**。
当前产品逻辑混乱、侧栏/例程臃肿。用户给了明确要求：

1. **侧栏瘦身**：去掉用不到的模块（面经库；助手/任务/审批/动态早已休眠）。
2. **例程裁剪**：草稿审阅、工作总结、会议准备、每日岗位推荐都不要了暂时；
   面试准备必须留（投递逐字稿依赖它）。
3. **必读只显 urgent+high**：不要"收件箱已分类"这类噪音，只保留从邮件中
   提取到的重要信息（招聘邮件、学校账单、导师消息等）——"只要收到邮件你
   认为是重要的你就应该在必读这里体现出来"，且要做到实时。
4. **草稿免审批**：写邮件 draft 应该直接由系统生成，不应再要用户确认一次。

Verified: typecheck + lint + 373 tests (1 skipped) + build 全绿；新
`tests/integration/email-briefing-service.test.ts` 5 测试 + 重写的
`approval-flow.test.ts` 5 测试（改用 `email.send_draft` 锚定 §15 闸）全绿。

## 决策

### 1. 侧栏 7→6（面经库休眠）

- `App.tsx` NAV 去掉 `InterviewNotes`、PAGE_LABELS、main mount、import。NAV 现
  6 项：首页 / 必读 / 投递 / 例程 / 记忆 / 集成与设置。
- `src/shared/types.ts` `WORKBENCH_PAGES` 去掉 `'InterviewNotes'`。
- **InterviewNotesPage 文件留盘作 dormant export**（镜像 Tasks/Activity/Assistant
  休眠模式，`export function` 满足 tsc noUnusedLocals）；后端 interview_notes
  store 方法 / schema / IPC 全保留不动（投递详情页仍读 prep_materials）。
- 审批 mount 继续保留（dormant 安全网，e2e 深链）。

### 2. 例程裁剪（移除 4 个 preset）

移除：`draft_review`、`meeting_prep`、`daily_work_summary`、`job_recommendation`。
保留：`morning_brief`、`auto_inbox`、`interview_prep`。

- 删模板文件：`draft-review.ts`、`meeting-prep.ts`、`daily-work-summary.ts`、
  `job-recommendation.ts`。
- `presets.ts` 去掉 4 import + `PRESETS` 4 项；`constants.ts`
  `PRESET_ROUTINE_IDS` 去掉 4 id。
- **`seedPresets` 补删除逻辑**：boot 时对 `RETIRED_PRESET_IDS` 走
  `store.deleteRoutine(id)`（直接走 store，绕过引擎 preset 保护，沿用 ADR 0020
  `deleteByTitle` 直接走 store 的先例）——否则移除 preset 的 DB 旧行残留被调度器
  继续跑。
- **agent action stub 保留 dormant**：`generate_meeting_prep`/
  `generate_work_summary`/`score_job_matches` 的 6-touchpoint 定义留在
  agent-runtime/structured-output/prompt-injection 不删（非用户可见；删除有 6 点
  lockstep 破坏风险，记入 follow-up）。`generate_draft_reply` 保留并复用（新自动
  草稿流要用）。
- RoutineBuilder 去掉 `meeting_prep` / `work_summary` step 模板（用户可见面）。

### 3. 必读页只显 urgent + high

- `NeedToKnow.tsx` 渲染前 `list.filter(n => n.priority==='urgent'||n.priority==='high')`；
  groups 数组去 medium；empty 文案"今日无紧急 / 重要事项"。
- 不改 morning brief（它仍产 medium NTK，页端过滤即不可见，符合"只看
  urgent/high"）。

### 4. 重要邮件 → 必读（实时，钩在同步回路）+ `EmailBriefingService`

新 `src/main/services/email-briefing-service.ts`。在 `container.ts`
`startEmailSyncLoop` 的 tick 里，`syncFromEmails` 返回后对 `result.newEmails`
跑 `classify_inbox`（复用既有 topic 检测：fees_billing/recruiting/meeting/ads/
general），对**重要**（topic ∈ {recruiting, fees_billing, meeting}）或
**actionable**（classification ∈ {reply, follow_up}）且非 untrusted 的邮件发布
NTK：

- priority = `topic==='recruiting'||topic==='fees_billing' ? 'urgent' : 'high'`
- title `【${TOPIC_LABEL[topic]}】${subject}`（招聘/账单/会议/广告/动态）
- **幂等**：游标增量是主闸（每封只处理一次）；额外用 `needToKnowService.list()`
  的 sourceRef `email:<messageId>` Set 防重试重跑双写。
- **untrusted（§17）邮件跳过**——绝不产 NTK、绝不草稿。
- **双分类可接受**：同步回路已对同一 delta 跑 `classify_application_email`
  喂投递漏斗；EmailBriefingService 再跑 `classify_inbox` 喂必读。两者职责不同
  （漏斗 vs topic/必读），delta 小（游标闸），双跑廉价。
- `syncFromEmails` 返回值加 `newEmails: NormalizedEmail[]`（去重增量 =
  `byMessageId.values()`），现有字段不变。
- NTK refetch 走 `onActivityChanged`（NTK 无专属 push channel）；briefing 在
  NTK 创建**之后**记 `tool_completed` Activity，确保 refetch 看见新 NTK。

### 5. 草稿免审批（§15 例外）+ 自动生成

- `tool-registry.ts` `email.create_draft`：`risk:'R3',requiresApproval:true` →
  `risk:'R1',requiresApproval:false`。注释标注 §15 例外（ADR 0022）：草稿创建是
  低风险插入用户自己的草稿箱，用户在邮件客户端审阅后手动发送；**真正的外部写
  是发送**，`email.send_draft` 保持 R3 / requiresApproval:true 不变。
- EmailBriefingService 对 `classification==='reply'` 且 important 的邮件自动生成
  草稿：best-effort `listSent({to:sender, sinceHours:720, limit:5})` 取用户自己
  的历史回复 → `runAgentStep('generate_draft_reply', {email, priorReplies, memory})`
  → `toolRegistry.execute('email.create_draft', {…}, toolContext)` R1 直执无暂停
  → 发"已草拟回复：…" high NTK 让用户去邮件客户端审阅发送。
- 节流：仅 reply 类 + important topic 才生成草稿（不是每封招聘邮件都回）；
  delta-bounded；no-LLM-key 走 stub（快），有 key 走真实模型。
- `generate_draft_reply` 输入形状：sent mail 经 `frameSentReply`（`<your_reply>`
  块，NOT `frameEmail`——`frameEmail` 调 `isUntrusted` 会误标引用注入邮件的回复）。

## 关键决策理由

- **草稿创建 R1 是 §15 例外，非破坏闸**：用户明确选"自动生成草稿免审批"。
  草稿只是写入用户自己的草稿箱（用户审阅后才发送），不是真正外部写；发送
  （`email.send_draft`）仍 R3 禁止。§15"approval gates every external write"的
  精神是防未经授权的外部副作用，草稿插入无外部副作用。注释 + 本 ADR 固化此例外。
- **必读实时性靠同步回路不靠例程**：用户要"收到邮件就体现"。例程
  `auto_inbox` 是 30min email_poll（慢）；同步回路是 ~3min per-provider 游标增量
  （快、独立于 scheduler.pause）。把 briefing 钩在同步回路 tick 而非新建例程。
- **止噪在源头不在页过滤**：ADR 0020 已删 auto_inbox 的 publish step（桶计数
  NTK 噪音）；本里程碑必读页端 urgent/high 过滤是"只看重要的"语义，非止噪 hack
  （噪音源头早根治）。
- **休眠非硬删**：镜像 ADR 0019 BOSS 退场 / ADR 0020 导航精简——删 nav 按钮 +
  模板文件，后端 service / agent action stub / store 方法全保留；一行挂回即可
  恢复。
- **`seedPresets` 必须删旧 preset DB 行**：seedPresets 是 insert/re-sync 语义，
  对从 PRESETS 移除的 id 不会清掉 DB 旧行 → 旧行残留被调度器继续跑。boot 删除
  是必要清理，走 store.deleteRoutine 绕过引擎 preset 保护（preset id 受引擎保
  护拒绝删）。
