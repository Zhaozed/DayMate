# ADR 0029 — 必读页重构：线程聚合 + 4 类分区 + 过滤放宽 + 去晨报化 + 标来源链接

> 状态：✅ 已落地（typecheck / lint / 461 tests / build 全绿）
> 日期：2026-08-23
> 前置：ADR 0022（必读=邮件驱动）、ADR 0023（群发确定性预过滤）、ADR 0027（ToDo 重构 + purgeVersion 闸）、ADR 0028（邮件过滤紧急修复）

## 背景

ADR 0028 把必读过滤收得很死（bulk 全丢、只 surface urgent/high），用户真机用下来对**必读页本身的形态**提出六点重做要求（原话浓缩）：

1. **标题错位**：页头叫"每日晨报"，但内容是邮件驱动信息汇总，与首页晨报卡无关。必读应是各来源信息汇总（现 Gmail+163，未来更多 APP），头标题不能再是"每日晨报"。
2. **无线程聚合**：同一邮件线程的多封邮件显示成多个独立卡片（如 `Re: Dissertation Title` ×3 各占一项）。要同一线程组合成一个 Item，且 Item 内**拉取该线程全部邮件**作上下文（含未判必读的），必读的标星。
3. **分类不符**：现按 priority（紧急/重要）分区 + 标题前缀 `【招聘/账单/会议/动态】`。要顶级标签重分 4 类：**学校 / 求职 / 日常 / 其他**，作分区标题分组。
4. **过滤太死**：ADR 0028 把所有 bulk 邮件（含操作触发类：投递确认/面试通知/回执）全丢。要放宽——纯广告不要；操作触发的邮件留下（验证码、安全提醒除外）。
5. **多余按钮**：顶部"运行晨报"+"清空全部"都要去掉（此 part 与晨报无关）。
6. **来源/链接不清**：sourceRefs 只显 `email：<subject>` 原始串，无 provider 徽章、无可点链接。要标清邮件来源 + 链接。

用户已确认 3 个关键决策（AskUserQuestion）：①线程 Item 拉取线程全部邮件做上下文；②4 类作分区标题分组；③163 也做线程聚合（从 References/In-Reply-To 头合成 threadId）。

## 改动

### A. 类型 + schema + DDL（新字段）

- `src/shared/constants.ts`：加 `BRIEFING_CATEGORIES = ['school','job','daily','other'] as const` + `type BriefingCategory`。**4 值**，与 Task 的 5 值 `TaskCategory`（学校/求职/账单/会议/其他，给 ToDo）**区分**——NTK 必读用 4 值分区，ToDo 不动。
- `src/shared/types.ts`：`NeedToKnow` 加 `threadId?: string`、`briefingCategory?: BriefingCategory`、`sourceProvider?: 'gmail'|'mail163'`、`sourceAccountId?: string`、`sourceLink?: string`、`updatedAt?: string`。`EmailClassificationResult` 加 `briefingCategory?: BriefingCategory`。
- `src/shared/schemas.ts`：加 `briefingCategorySchema`；`classificationSchema` 加 `briefingCategory` 可选字段（**不替换** 5 值 `category`——ToDo 仍用 5 值；NTK 用 4 值 briefingCategory）。
- DDL/迁移：`schema.ts` ntk 表加 `thread_id`/`briefing_category`/`source_provider`/`source_account_id`/`source_link`/`updated_at` 列；`migration.ts` CREATE TABLE 加列；`client.ts` `applyGuardedAlters` 加 6 个 `addColumnIfMissing`（M1 幂等 pattern）；`sqlite-store.ts` `rowToNtk` + `createNeedToKnow` + `updateNeedToKnow` 透传；`in-memory-store.ts` 同步；`store.ts` 接口加 `updateNeedToKnow(id, patch)`。

### B. 线程 threadId 填充（provider 层）

- **163**（`mail163-provider.ts` `toNormalized`）：合成 `threadId` —— 取 References 首 `<...>` token（会话根，每封回复共享）；退 In-Reply-To；再退自身 Message-Id（根邮件两者皆无）。新增 `firstAngleToken`（取 `<...>` 首段、剥角括号、对 mailparser `.get()` 的非字符串返回值 coerce）+ `synthesizeThreadId`（导出，纯函数）。**关键不变量**：根邮件的 Message-Id 也剥角括号，使其与回复里引用的 bare id 匹配（mailparser 的 `messageId` 带角括号，References token 不带 → 不剥会 mismatch，线程合并不命中）。零新依赖（headers map 已转发）。
- **Gmail**：`threadId` 已填（`normalizeGmailMessage`），不动。

### C. 线程合并 + 字段透传（briefing service）

`email-briefing-service.ts` `briefNewEmails`：
- **过滤放宽**：`humanEmails = realEmails.filter(e => !shouldSkipBriefing(e))`（见 D）。操作触发 bulk（投递确认/面试通知/报名成功/收据/回执）不再被 pre-LLM 闸硬丢，而是继续流到 classify_inbox——这是相对 ADR 0027/0028「全丢 bulk」的放宽。
- **surface gate = `important || actionable`（修正）**：`important=IMPORTANT_TOPICS.has(topic)`（recruiting/fees_billing/meeting）|| `actionable=reply/follow_up`。**LLM `ignore` 判定始终尊重**（`if (r.classification==='ignore') continue`，bulk 亦然）。
  > v7 原版有一 `operationTriggered = isBulkMail(email)` 臂，对凡过 pre-LLM 闸的 bulk 强制 surface 为 `medium` 并覆盖 LLM `ignore`——结果 Grab / 马来促销「Flash Sale / Deals / Diskaun / happier prices」这类窄 `ADS_KEYWORD_RE` 漏网的营销 bulk 涌进必读（用户「啥内容都没有啊」）。v8 修正：删该臂，surface 回归 `important || actionable`。用户真正在意的操作触发邮件本就落 important topic（投递/面试→recruiting、账单/收据→fees_billing、会议/邀请→meeting），靠 topic 闸即可捕到，无需那把会放进营销垃圾的 blanket bulk 覆盖。general-topic 的 bulk（Grab 促销、邮件确认信、GitHub OAuth）即便模型（或 stub）判 `information` 也不 surface。
- **priority**：recruiting/fees_billing→urgent；其余 important/actionable→high（无 medium 臂）。
- **title**：`r.reason || email.subject`（**ADR 0029 fix**：标题=模型中文总结，原邮件标题降为副标题——用户要「你总结的中文放醒目位置，真邮件标题放下面」。原 subject 仍存于 `sourceRefs[].label`，renderer 取末项作副标题；title===副标题时隐藏。stub 路径 reason 含发件人名+topic（如 `Alice Chen 期待你回复`、`Tuition Office：账单通知`）——用户明确要导师名写上）。
- **线程合并**：`const existing = email.threadId ? needToKnowService.list().find(n => n.threadId===email.threadId && n.sourceProvider===email.provider && n.sourceAccountId===email.accountId) : undefined`。命中 → `needToKnowService.update(existing.id, { title, summary, sourceRefs: append-if-absent, briefingCategory })`；否则 → create 新 NTK，带 `threadId`/`briefingCategory`/`sourceProvider`/`sourceAccountId`/`sourceLink`。`seen` set 仍按 `email:<messageId>` 防 sourceRef 重复（幂等）。
- `briefingCat = r.briefingCategory ?? TOPIC_TO_BRIEFING[topic] ?? 'other'`。
- autoDraftReply：仍只对 `reply + important`（回执/确认信多为 information 非 reply，本就不草稿）。

### D. 过滤放宽（bulk-mail.ts + prompt）

- `src/main/util/bulk-mail.ts`：
  - 加 `VERIFICATION_CODE_RE`（验证码/verify code/OTP/动态码/…）+ `SECURITY_ALERT_RE`（安全提醒/异地登录/new login/suspicious/…）。
  - `shouldSkipBriefing(email, tokens)` 改为三段：isSchoolSpam→skip；非 bulk→keep（classify）；bulk 则 `ADS_KEYWORD_RE`（纯广告）/`VERIFICATION_CODE_RE`（验证码）/`SECURITY_ALERT_RE`（安全提醒）任一命中→skip，否则 keep（操作触发 bulk：投递确认/面试通知/报名成功/收据/回执/opted-in deploy-status → 留下，classify）。镜像 funnel 的 `isBulkMail && ADS_KEYWORD_RE` 模式（`shouldSkipFunnel` 不变）。
- `src/main/agent/prompt-injection.ts` classify_inbox task：**放宽 automated→ignore 硬规则**。改：automated/no-reply 邮件分两类——**操作触发的自动邮件**（直接回应用户动作：投递确认/简历已收到/面试通知/报名成功/收据/发送回执/opted-in deploy-status/订单状态）→ `information`（surface），填 `briefingCategory`；**未经请求的营销/edm/newsletter/促销** → 仍 `ignore`。`briefingCategory` **每封 surface 邮件都填**（school=学院/专业/教务/导师/私人学校事务；job=求职/招聘/面试/投递；daily=账单/缴费/会议/日程/订单/日常；other=其余）。多层纵深防御不变。
- **§17 不变**：untrusted 邮件 `enforceTrust` 仍剥 todoTitle/dueDate/category/**briefingCategory**（新增字段也剥，防注入）；bulk/spam/codes/alerts 在 pre-LLM 闸跳过。

### E. 整线程上下文拉取（新 IPC + provider）

- `src/shared/constants.ts`：加 `EMAIL_THREAD_GET: 'daymate:email:thread:get'`。`types.ts` `DaymateApi` 加 `getEmailThread({threadId, provider, accountId}): Promise<NormalizedEmail[]>`。
- `email-provider.ts`：接口加 `getThread?(threadId): Promise<NormalizedEmail[]>`（可选，无 threading 的 provider 返 []）。
- **Gmail**：`getThread(threadId)` → `gmailGet(accessToken, /users/me/threads/{id}?format=full)` → `{messages: GmailMessageRaw[]}` → 每条 `normalizeGmailMessage` → 按 receivedAt 升序返。原生 threadId。
- **163**：`getThread(threadKey)` → `getMailboxLock('INBOX')` → 三路 `safeSearch`（references / in-reply-to / message-id 头匹配 threadKey，每路 try/catch 返 []）→ 去重 uid → `fetchOne`+`toNormalized` → 升序。**best-effort**：搜索为空或抛错 → 返 `[]`（renderer 回退到只显 surfaced sourceRefs）。新增 `safeSearch` helper（IMAP 头搜索在 163 上不可靠，错即返空，永不抛给 renderer）。
- `handlers.ts`：handler `EMAIL_THREAD_GET` → 按 `(provider, accountId)` 在 `container.emailProviders` 找实例 → `provider.getThread`。try/catch 返 []。**R0 只读**（§15 无外部写）。
- `preload/index.ts`：暴露 `getEmailThread`。

### F. 必读页 UI 重做（NeedToKnow.tsx + labels.ts）

- **页头**：标题 `每日晨报`→`必读`，副标题"各来源信息汇总 · 按线程聚合 · 学校/求职/日常/其他"。**删**"运行晨报"按钮 + "清空全部"按钮（整个 Header 按钮区去掉，只留标题）。保留 per-item 忽略按钮。
- **过滤放宽**：删 `n.priority==='urgent'||'high'` 过滤 → 显全部 surfaced（urgent+high+medium，curation 已在 pre-LLM+surface 闸）。
- **4 类分区**：按 `briefingCategory` 分 4 组，顺序 `BRIEFING_CATEGORY_ORDER = school→job→daily→other`；每组 section header（`▍学校` + 数量）。组内按 `updatedAt ?? createdAt` 倒序（线程有新回复冒顶）。
- **线程 Item**（替代单卡）：每 NTK 一项——头：`title` + `· N 封`（N=sourceRefs.length）+ priority 小徽章（urgent红/high橙/medium灰）+ source provider 徽章；体：summary + reason；`sourceLink` 存在 → provider 徽章包 `<a target=_blank>`（Gmail 真深链；163 链 webmail 根，不造假深链）；**展开**：lazy `getEmailThread({threadId, sourceProvider, accountId})` → 渲染线程全部邮件（升序），sourceRefs 含的 messageId 标 `★`，其余普通行；loading/空态回退只显 surfaced。`ThreadExpansion` 组件 local state 缓存、cancel flag。
- `labels.ts`：加 `BRIEFING_CATEGORY_LABEL`（school→学校/job→求职/daily→日常/other→其他）+ `BRIEFING_CATEGORY_ORDER` + `PROVIDER_LABEL`（gmail→Gmail/mail163→163）+ `SOURCE_REF_TYPE_LABEL`（备用，email→邮件/…）。
- accountId 传递：NTK 加 `sourceAccountId` 字段（A 节加），create 时透传 `email.accountId`；getEmailThread 用之（未来多账号可靠，不从 provider 单账号推断）。

### G. purge 重建（PURGE_VERSION→7）

- `container.ts`：PURGE_VERSION 6→7（v8 修正）。v7：旧 NTK 是 one-per-email、无 threadId/briefingCategory/sourceProvider/sourceLink，新 4 分区线程页会把它们全归到「其他」无来源徽章无展开——purge 清，coldStartDone 重置→re-backfill 用新 `briefNewEmails`（线程合并 + 新字段 + 放宽过滤）重建。**v8**：v7 的 `operationTriggered` 覆盖臂把 Grab/马来营销 bulk 当操作触发 surface 成 medium（用户「啥内容都没有啊」）——purge 清这批垃圾 NTK（实测 77 条），coldStartDone 再重置→re-backfill 用修正后 `important||actionable` 闸重建（mail163 83 封扫描，必读 27→1）。漏斗不受影响（游标推进，purge 不重建投递）。

## 设计取舍 / 风险

- **one-NTK-per-thread by list() scan**：合并靠扫 `needToKnowService.list()` 找同 threadId——NTK 量小（百级），线性扫描可接受；无需新索引/store 方法。同批次同线程：第一封 create、后续 merge（in-memory/sqlite list() 反映刚插入）。
- **整线程 lazy 不持久化**：线程全部邮件不存库（重 + §17），展开时按需 getEmailThread；renderer 缓存。163 IMAP header search best-effort，空/错回退 surfaced-only。
- **4 值 vs 5 值 category**：BriefingCategory(4) 给 NTK 分区；TaskCategory(5) 给 ToDo 不动。LLM 输出两字段（briefingCategory 每 surface 必填 + category todoTitle 时填）；stub 都填。避免改动 Task/funnel schema。
- **过滤放宽 ≠ 回到垃圾**：三层纵深（pre-LLM 闸 drop ads/codes/alerts/spam → LLM prompt unsolicited→ignore / 操作触发→information → surface 闸 `important || actionable`，LLM `ignore` 始终尊重）。操作触发 bulk 现在能到 LLM（取代 ADR 0028 全丢），但 surface 仍需 important topic——投递/面试/账单/会议才进必读，Grab 促销等 general-topic bulk 不进。v7 曾用 `operationTriggered` blanket 覆盖臂放进营销垃圾，v8 删除（见 C 节修正块）。
- **去 priority 过滤**：页面显全部 surfaced（curation 在闸），priority 降为项内小徽章。覆盖 ADR 0022 urgent/high-only（用户明确要放宽）。
- **163 无真深链**：sourceLink=`https://mail.163.com/`（webmail 根），徽章可点但不定位到具体邮件——诚实，不造假深链。
- **sourceAccountId 新字段**：getEmailThread 需 accountId 定位 provider 实例；NTK 加 sourceAccountId（A 节加）。
- **firstAngleToken coerce**：mailparser `.get()` 对 list-valued 头可能返非字符串（数组）；coerce 成字符串再 match。根 Message-Id 剥角括号保证与回复引用的 bare id 匹配。
- **PURGE_VERSION→7**：清旧 NTK 重建为线程合并形；cold-start re-backfill 重建。漏斗不受影响。
- **§17**：untrusted enforceTrust 剥 briefingCategory（新增字段也剥，防注入）；bulk/spam/codes/alerts pre-LLM 跳过。§15 不受影响（NTK=本地写 R1；getEmailThread=R0 只读）。

## v9 后续修正（用户反馈）

1. **标题=中文总结，原 subject 降副标题**：NTK.title 从 `email.subject` 改 `r.reason || email.subject`。renderer NtkItem 醒目显示 title（模型中文总结），下方小字取 `sourceRefs[末].label`（原邮件标题）；title===副标题时隐藏。stub reason 升级含发件人名+topic（`Alice Chen 期待你回复` / `Tuition Office：账单通知`），不再裸 `发件人期待回复` / `无需回复`。
2. **ToDo todoTitle 放宽 25→40 字**：prompt `≤25 chars` → `≤40 chars`（classify_application_email `≤20` → `≤40`），并要求 INCLUDE THE SPECIFIC PERSON（导师/HR 名，非仅「导师」）——用户「导师的名字你得写上」。
3. **点操作后跳顶修复**：根因 `useAsync` refetch 设 `loading=true` → 页面 `if(loading) return <Loading/>` 整棵卸载列表 → 滚动位置丢。修：useAsync 用 `dataRef` 区分首屏（data 空→显示 Loading）与 refetch（data 有→保留列表静默刷新，loading 不置 true）；NeedToKnow 改 `loading && list.length===0` / `error && list.length===0` 守卫，已有数据时 refetch 不卸载。
4. **PURGE_VERSION→9**：旧 NTK 创建时 title=subject，purge + re-backfill 用新 title=reason 重建。
