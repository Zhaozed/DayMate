# ADR 0028 — 邮件过滤紧急修复（必读垃圾 + 假投递 + 漏斗置信度 + demo 再种）

> 状态：✅ 已落地（typecheck / lint / 440 tests / build 全绿；双账号真机验证）
> 日期：2026-08-23
> 前置：ADR 0022（必读=邮件驱动）、ADR 0023（群发确定性预过滤）、ADR 0027（ToDo 重构 + 冷启动回填 + purgeVersion 闸）

## 背景

ADR 0027 落地后真机跑起来，用户两次强烈反馈过滤"真实废物"：

1. **必读里全是垃圾**：招聘广告（LinkedIn "jobs you may be interested in"）、学校 `[student_ips]` 群发广播、Railway/GitHub Actions 自动部署通知全进了必读；有用的反而被筛掉。原话："招聘广告你也给我放进来。学校ips广告邮件给我当成我已经投递过的内容，你成功的把有用的筛掉了留了一堆没有的，真实废物。"
2. **投递里全是假投递**：5 条 Universiti Malaya RA/PhD——这些是**招聘外联邮件**（announces an open position, invites the candidate to apply），漏斗把它们当成用户已投递建了投递。原话："请问正确个单啊，我啥时候投递过？？？？？？？？？？" 另有 10 条 `demo:` 前缀的 AI产品经理 demo 投递（`seedDemoData` 每次 boot 重种），真实 provider 已连，demo 数据是噪音。

根因有四，本 ADR 逐一修复。

## 改动

### A. 必读 surface 尊重 LLM `ignore` 判定（surface 逻辑）

**根因**：`EmailBriefingService.briefNewEmails` 的 surface 逻辑在 `if (r.untrusted) continue` 之后**直接进 topic 闸**，没看 LLM 自己的 `classification`。LLM 把 LinkedIn 群发招聘广告正确判成 `ignore`（"营销性资讯，无待办"），但 topic=`recruiting` 命中 `IMPORTANT_TOPICS` → 仍当 urgent surface。`ignore` 判定被丢掉了。

**修**：在 untrusted 检查之后、todoTitle 建任务 + important/actionable 检查**之前**加：
```ts
if (r.classification === 'ignore') continue
```
`ignore` = FYI / newsletter / automated-marketing，无人类可执行下一步 → 不产必读、不产 ToDo（todoTitle 在 ignore 上本就该空，enforceTrust + prompt 都禁，此处防御纵深防模型漏填）。先于 todoTitle 检查跑，ignore 永不携带 todoTitle。

**测**：`tests/integration/email-briefing-service.test.ts` 加「必读 surface respects LLM ignore」——mock runtime 返 `classification:'ignore'` + `topic:'recruiting'`（sender `talent@linkedin.com`，非 bulk，所以到 classify_inbox；LLM 正确返 ignore）→ 断言 surfaced=0、tasksCreated=0、无 NTK、无 ToDo。

### B. 删除必读 bulk-surface 路径（29 条垃圾的真凶）

**根因**：`briefNewEmails` 旧有一个 deterministic bulk-surface 循环——对 bulk 邮件正文跑 `IMPORTANT_BULK_KEYWORD_RE`（毕业/缴费/答辩/…），命中就 surface `【通知】${subject}`。但 LinkedIn / 游戏 / 营销正文里也提 注册/offer/面试/招聘 → 29 条 `【通知】` 垃圾漏进必读，正是用户说的"招聘广告你也给我放进来"。

**修**：整段 bulk-surface 循环删除。bulk 邮件（LinkedIn 招聘广告 / 游戏通知 / 平台 digest / 系统自动通知 / mailing-list 广播）**永不进必读、永不产 ToDo、零 LLM**。只 `realEmails.filter(e => !isBulkMail(e))` 的真人邮件走 classify_inbox。学校行政 bulk（毕业/缴费经 list 发）在严格标准下是可接受损失；真正一对一学院邮件仍走 human path。`IMPORTANT_BULK_KEYWORD_RE` 从 import 移除（`isBulkMail`/`isSchoolSpam` 保留）。

**测**：`email-briefing-service.test.ts` 旧「bulk mail with important keyword」测试从 surfaced=1 改成 surfaced=0；`shouldSkipBriefing`（`bulk-mail.test.ts`）所有 bulk（含 important 关键词）现在都 skip。

### C. 漏斗置信度闸（假投递根因）

**根因**：`ApplicationService.syncFromEmails` 旧逻辑"Aggressive: company+position extracted → create even at low confidence"——只要抽出公司+岗位就建投递，不看 confidence。招聘外联邮件（Universiti Malaya RA position available）抽出公司+岗位 → 建假投递。

**修**：建投递分支前加置信度闸：
```ts
if (r.confidence === 'low' || !r.company || !r.position) {
  this.pushPending(r, email, undefined); pending++; continue
}
```
low confidence 或缺公司/岗位 → 进 pending 队列，**不建投递**。只有 high/medium confidence + 公司 + 岗位才建。漏斗是增量游标的，purge 清掉的假投递不会被重建；新真实进度事件走严格闸。

**测**：`tests/unit/email-inference.test.ts` 加「low-confidence recruiting-outreach mail → pending, NOT auto-created」——subject "RA position available"，body "We have an open Research Assistant position. Reach out if interested."（**body 不含 "apply"**——stub 的 applied 正则会匹配成 medium，要避开）→ stub confidence=low → pending、created=0。

### D. prompt 强化（让 LLM 判对）

**`classify_inbox`**（`prompt-injection.ts`）加：MASS / AUTOMATED / NO-REPLY 邮件**必须判 `ignore`**（不是 `information`）——营销招聘活动（LinkedIn "jobs you may be interested in"…）、newsletter、促销/edm、自动系统通知（Railway/GitHub Actions/Sentry 部署/CI/监控/crash/status…）。`information` 留给真人发来的、需要你知悉的 genuine personal FYI。拿不准选 `ignore`。`ignore` = 无必读、无 ToDo（todoTitle 必空）、无草稿。

**`classify_application_email`** 加 CONFIDENCE RULE（critical — 防假投递）：任何**招聘外联 / 招揽**——邮件宣布一个 OPEN position 并邀请候选人投递——返 `confidence:low`。这些**不是**投递进度事件：候选人还没投。只有确认候选人**已采取的动作**或候选人真正所处的阶段才返 high/medium。

**注意**：用户用真实 deepseek LLM（key 已配），classify 是非确定性的。prompt + 确定性 bulk/spam 闸 + surface 闸 + 置信度闸是多层纵深防御，不是单点依赖 LLM。

### E. bulk 检测拓宽（catch jobs-noreply / alerts@railway）

**根因**：`bulk-mail.ts` 旧 `BULK_SENDER_RE = ^(noreply|no-reply|...)@` 只匹配 local-part **开头**。`jobs-noreply@linkedin.com`、`railway-noreply@railway.app` 这种复合地址匹配不到 → 漏到 LLM → 招聘广告 / 部署通知进必读。

**修**：拆成两个正则：
- `BULK_SENDER_CONTAINS_RE`（local-part **任意位置**匹配，catch `jobs-noreply@`、`railway-noreply@`、`mailer-daemon`、`auto-reply`…）
- `BULK_SENDER_PREFIX_RE`（开头匹配 CI/监控/deploy/alert bot 前缀：notice/notification/alert/monitor/deploy/ci/bot/system/admin/status…）

`isBulkMail`：`bulk` flag OR contains RE OR prefix RE OR school-list alias in To。

### F. demo 投递再种 tug-of-war（demoSeeded 闸）

**根因**：`seedDemoData()` 的 `hasRealData` 守卫把它自己的 demo 行（source='email' + 真公司+岗位）当"real" → 版本化 purge 清掉 demo 行后守卫失效 → 下次 boot seedDemoData 看到空漏斗 → **再种 10 条 demo 投递** → purge 版本追上后不再清 → demo 行靠 hasRealData 守卫稳态存活。真实 provider 已连的用户永远看到 10 条假 AI产品经理 投递（"我啥时候投递过"）。

**修**：
- `TodoSettings` 加 `demoSeeded?: boolean`（`types.ts` + `settings.ts` `normalizeTodo` 透传）。
- `container.ts`：`seedDemoData()` 从同步调用点（466）移进 purge IIFE，**gated by `!todo.demoSeeded`**，种完 `writeTodo({ demoSeeded: true })`。flag **永不被 purge 重置**（purge 只写 purgeVersion/purgeDone/coldStartDone/skipTokens，writeTodo MERGE）。
- `PURGE_VERSION` 3→4：v4 再清一次 demo 投递（所有当前 source='email' 投递都是 `demo:` 前缀，无真实 email-inferred 投递可丢，安全）。之后 demoSeeded=true 阻止再种，purgeVersion=4 不再清 → demo 投递**永久 0**。
- 版本史：v2 = 尊重 LLM ignore + 漏斗置信度闸；v3 = 必读彻底丢 bulk；v4 = 清 demo tug-of-war（demoSeeded 堵住再种）。

**测**：`tests/unit/settings-todo.test.ts` 加 demoSeeded round-trip + 跨 purge writeTodo 存活测；`tests/unit/todo-purge.test.ts` 已覆盖 source='email'（含 `demo:` 前缀）投递被清。

## purge-backfill 竞态（已知，可接受）

v4 purge 跑的那一次 boot，gmail connect-backfill 可能在 purge `finally`（`resolvePurgeGate`）resolve 之前先跑（connect 事件触发的 `triggerColdStartIfNeeded` 虽 `await purgeSettled`，但实测 timeline 偶有乱序）→ purge 把 gmail 这一轮的 surface 结果也清了。**只影响 v4 那一次 boot**；之后 purgeVersion=4 → 不再 purge → 无竞态 → 增量 sync loop 持续 surface 新到的有用邮件。下一次 boot coldStartDone 重置后 gmail re-backfill 重建。非过滤 bug，是 one-shot 竞态，不修（再 bump 版本反而复现）。

## 设计取舍 / 风险

- **bulk 严格丢弃**：学校行政 bulk（毕业/缴费经 list 发）也丢——严格标准下可接受损失；一对一学院邮件仍走 human path。
- **demo 数据对 fresh install**：demoSeeded 闸 + v4 purge 使 fresh install 也不再长期存 demo 投递（种完即被 v4 清）。dev 想要 demo 数据需手动 `demoSeeded:false` + `purgeVersion<4`。用户明确不要假投递，优先用户诉求。
- **漏斗增量不可重建**：purge 清真实 email-inferred 投递后，游标已推进 → 不重建。当前无真实 email-inferred 投递（全是 demo），v4 安全。未来若有真实投递，bump purge 版本会丢它们——记此风险，慎 bump。
- **LLM 非确定性**：classify 结果 run-to-run 不同（deepseek）。多层确定性闸（bulk/spam/ignore-surface/confidence）+ prompt 是纵深防御，不单点依赖 LLM 判对。
- **§17**：untrusted 邮件 `enforceTrust` 仍剥 todoTitle/dueDate/category（不变）；bulk/spam 在 pre-LLM 闸确定性跳过。§15 不受影响（ToDo=本地写 R1；settings IPC=本地读写 R1）。

## 第二轮修复（v5/v6 — mock 日历泄漏 + ToDo 标题缺主语）

> 同一 ADR 追加——同一"邮件过滤紧急修复"主题的续轮，用户两问驱动。

### 背景（用户两问）

v4 稳态后用户又提两问题：

1. **"Decide: Approval Center in P0 or defer for Q3 roadmap 这是个啥？"** —— UI 里冒出一条 `Decide: Approval Center in P0 or defer for Q3 roadmap` 的 ToDo + 一条"Q3 roadmap review"晨报。用户没创建过这些。
2. **"ToDo总结的不好，缺少主语，'回复导师附上附件'回复啥子？还有你写的根据付款失败问题，跟进什么的付款失败？太精炼了都"** —— ToDo 标题太精炼，缺具体对象/上下文。"回复导师附上附件"回复啥？"跟进付款失败问题"哪个付款？用户不打开邮件看不出指的是什么。

### G. mock 日历泄漏（Q3 roadmap / Approval Center 的根因）

**根因**：ADR 0025 只在真实 **邮件** provider 连接时 splice 掉 mock **邮件** provider，但 mock **日历** provider（`MockCalendarProvider`，accountId `mock-feishu-001`）未被处理——Feishu 未连 → mock 日历一直 active → `FIXTURES` 里的 `mock-evt-001 "Q3 roadmap review"` + `mock-evt-002 "1:1 with manager"` 喂给 `morning_brief` routine → routine 抽出 `Decide: Approval Center in P0 or defer for Q3 roadmap` 这条 ToDo（sourceType='routine', sourceId='mock-msg-001'）+ "Q3 roadmap review" 晨报 NTK。这正是"这是个啥"。

**根因二（清理盲区）**：v2–v4 purge 只清 `sourceType='email'` task + `sourceRefs.type==='email'` NTK。routine 抽出的 mock ToDo（sourceType='routine'）不在清范围；"Q3 roadmap" 晨报 NTK 是 `kind='morning_brief'` + `sourceRefs.type='calendar'`，purge 的 `list()` 排除 dismissed + 排除 morning_brief → 看不到，`listMorningBriefs` 只返未 dismissed 的 → **用户 dismiss 过的 mock 晨报 NTK 永远清不掉**（`list()` 排 dismissed，`listMorningBriefs` 不含 dismissed）。

**修（双层）**：

1. **mock 日历 realMode 静默**（`mock-calendar-provider.ts`）：加 `realMode` flag + `setRealMode(on)`。`listEvents` 在 realMode 下直接返 `[]`——真实用户连了真实邮件 provider 后，mock 日历 fixture 不再喂 routine。`container.ts` 在 `refreshEmailProviders`（mock 邮件 splice 之后）+ `refreshCalendarProvider` backstop 调 `mockCalendar.setRealMode(hasRealEmail)`。源头断流，不再产生新的 mock 晨报/ToDo。
2. **purge v5 + v6 清存量**（`todo-purge.ts` + `container.ts` PURGE_VERSION→6）：
   - **v5**：purge 的 task 循环加 `mockSourced = sourceType==='routine' && sourceId.startsWith('mock-')` → 清掉 routine 抽出的 mock ToDo（"Decide: Approval Center"），保留真实 routine task（sourceId 是真实 messageId，如 `19fe857b1eefa60f`）。NTK 循环加 `listMorningBriefs(365)` 扫描 + `isMockMorningBrief`（title/summary 含 `Q3 roadmap`/`Q3路线图`/`Approval Center`/`审批中心`/`roadmap review` 或 sourceRef id 以 `mock` 开头）→ 清 mock 晨报 NTK。
   - **v6**：v5 后仍有 2 条 mock NTK 残留——用户在真实 provider 连之前 dismiss 过它们（`ntk_22403d94 "Morning Brief: Q3 Roadmap Decision Due Friday"`、`ntk_dc6d6bf0 "【动态】Q3 roadmap review"`），`dismissedAt` 已设 + `kind=null`（非 morning_brief）→ `list()` 排 dismissed 看不到 + `listMorningBriefs` 不含 → 漏网。v6 加 `listAllNeedToKnow()` store 方法（**含 dismissed**，全表扫描 newest-first），service 暴露 `listAll()`，purge 的第二循环改扫 `listAll()` + 泛化 `isMockMorningBrief`→`isMockNtk`（同谓词，作用于任意 kind）→ dismiss 过的 mock NTK 也清掉。`listAllNeedToKnow` 加进 `store.ts` interface + `sqlite-store.ts`（`SELECT * FROM ntkTbl ORDER BY createdAt DESC`，无 WHERE）+ `in-memory-store.ts`（全表）。

**测**（`tests/unit/todo-purge.test.ts`）：① routine-extracted mock ToDo（sourceId `mock-msg-001`）被清 + 真实 routine task（`19fe857b1eefa60f`）保留；② mock-sourced morning_brief NTK（Q3 roadmap calendar sourceRef）被清 + 真实 morning_brief（导师组会）保留；③ **DISMISSED** mock NTK（用户 dismiss 过的 "Morning Brief: Q3 Roadmap Decision Due Friday"）被 v6 清 + dismiss 过的真实 NTK（"回复导师：确认论文题目"，无 mock marker）保留。

### H. ToDo 标题缺主语（todoTitle prompt 强化）

**根因**：`classify_inbox` 的 LLM 指令把 `todoTitle` 限 ≤20 字 + 只说"概括要做的事"，deepseek 实测就把具体对象省了——产出 "回复导师附上附件"（回复啥？）、"跟进付款失败问题"（哪个付款？）。用户要看标题就知道指什么，不必打开邮件。

**修**（`prompt-injection.ts` classify_inbox task 的 todoTitle 指令）：
- 字数限放宽 ≤20→**≤25 字**。
- 加**硬要求**：todoTitle **必须包含具体对象/上下文**（回复什么、哪个账单/付款失败、跟进什么），从邮件 **正文** 派生，具体到用户不打开邮件就知道指什么。
- 加 good/bad 示例（bad 用用户原话投诉的标题）：
  - Good：`回复导师：确认论文题目`、`跟进建行付款失败`、`跟进 MAYA 考官录入`、`确认字节面试时间`。
  - Bad（太精炼、无对象，用户看不出指什么）：`回复导师附上附件`、`跟进付款失败问题`、`回复 HR`、`跟进导师`。
- 仍禁止逐字复制邮件主题（防 `跟进：1677387239` 不可读）；外文专有名词可保留英文。

**注意**：stub（`agent-runtime.ts` classifyInbox）未改——用户用真实 deepseek LLM，todoTitle 来自模型非 stub。stub 的 `跟进/回复 ${who}（${topicLabel}）` 仍是 deterministic fallback。
